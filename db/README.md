# @usg/db

The PostGIS schema (PostgreSQL 18 + PostGIS 3.6) as dbmate migrations, a generated snapshot of it, and the database rule tests. Run the commands from the repo root once the local stack is up (see [Local stack](../README.md#local-stack) in the root README).

| Path | What it is |
| --- | --- |
| `migrations/` | The schema, as dbmate migrations in plain SQL. The first, `*_initial_schema.sql`, is the draft v1 with the comments that explain the model |
| `schema.sql` | Generated by `pnpm db dump`: `pg_dump --schema-only` of a freshly migrated database. Do not edit |
| `scripts/dbmate.ts` | dbmate with this repo's settings: `pnpm migrate` (`up`), `pnpm db status`, `pnpm db new <name>`, `pnpm db rollback --yes` |
| `scripts/dump.ts` | `pnpm db dump` |
| `src/` | Shared by the scripts and the tests: paths and `.env` loading, the dbmate runner, scratch databases, the dump normaliser |
| `test/db/` | The database rule tests, `pnpm test:db` (needs PostGIS) |
| `test/unit/` | Tests that need no database, part of `pnpm test`: the dump normaliser, and the settings repeated across `docker-compose.yml`, CI and `.env.example` |

## Settings

`DATABASE_URL` comes from the environment or the root `.env`. The scripts run the dbmate binary from the `dbmate` npm package with `DBMATE_MIGRATIONS_DIR` set to `db/migrations` and `DBMATE_NO_DUMP_SCHEMA`, since dbmate's own dump needs a `pg_dump` on the host that matches the server.

The app database (`usg`) is created by `pnpm migrate`, from `template1`. The PostGIS image's init script loads PostGIS, topology and the tiger geocoder into `POSTGRES_DB`, so the compose file keeps that as `postgres`: the app database then holds only what the migrations create, the dump stays clean, and the initial migration's down section can drop PostGIS.

## The schema snapshot

`pnpm db dump` applies every migration to a scratch database, runs `pg_dump --schema-only --no-owner --no-privileges` inside the PostGIS container (`docker compose exec postgis`, or `docker exec $PG_CONTAINER` in CI), and drops the scratch database. It then removes what changes between runs or servers (the `\restrict` lines with their random key, the version comments, CRLF and runs of blank lines), adds a generated-file header and appends the applied versions in dbmate's format. The output is the same on Windows and Linux. CI's `Database (postgis)` job regenerates it and fails on a diff.

The snapshot is schema only: the `map_head` row that the initial migration inserts is not in it, so build databases with `pnpm migrate`, never from `schema.sql`.

## Rule tests

Each rule in the schema has a test with a passing case and a refused case. A refused case checks why it was refused, not just that it failed: the SQLSTATE plus the constraint name (CHECK, UNIQUE, FOREIGN KEY) or the trigger's message. The fixtures are synthetic, at real City Hall cluster coordinates; the restricted zones are made up, never real outlines.

- The global setup migrates a template database with dbmate. Each test file copies it into its own database, so files run in parallel, and drops it afterwards; the developer's `usg` database is never opened. All of these are named `usg_scratch_<epoch ms>_<label>_<hex>`, and a run drops any left over from a crashed run more than an hour old.
- Inside a file, tests run in a transaction that is rolled back (`db.rolledBack`). Deferred rules fire at COMMIT ("every version except a rollback publishes a change set"), so their tests commit for real (`db.committed`, `db.expectCommitRefused`) in the file's own database.
- A change to a rule goes in a new migration with its tests in the same change.
