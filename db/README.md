# @usg/db

The PostGIS schema (PostgreSQL 18 + PostGIS 3.6) as dbmate migrations, a generated snapshot of it, and the database rule tests. Run the commands from the repo root once the local stack is up (see [Local stack](../README.md#local-stack) in the root README).

| Path | What it is |
| --- | --- |
| `migrations/` | The schema, as dbmate migrations in plain SQL. The first, `*_initial_schema.sql`, is the draft v1 with the comments that explain the model; later ones say in their header what they change and why (`*_levels_name_unique_deferrable.sql`: a venue's level names are checked once a change set is in, so two levels can swap names) |
| `schema.sql` | Generated by `pnpm db dump`: `pg_dump --schema-only` of a freshly migrated database. Do not edit |
| `scripts/dbmate.ts` | dbmate with this repo's settings: `pnpm migrate` (`up`), `pnpm db status`, `pnpm db new <name>`, `pnpm db rollback --yes` |
| `scripts/dump.ts` | `pnpm db dump` |
| `scripts/seed.ts`, `seed/` | `pnpm db seed`: the seed script and its dataset, the core venues (see [Seed script](#seed-script)) |
| `src/` | Shared by the scripts and the tests: paths and `.env` loading, the dbmate runner, scratch databases, the dump normaliser, the seed mechanism (`seed.ts`), the demo map's markers (`demo.ts`) and recreating the local database (`local.ts`) |
| `test/db/` | The database rule tests, plus the seed script's and `local.ts`'s, `pnpm test:db` (needs PostGIS) |
| `test/unit/` | Tests that need no database, part of `pnpm test`: the dump normaliser, `isLocalHost`, and the settings repeated across `docker-compose.yml`, CI and `.env.example` |

## Settings

`DATABASE_URL` comes from the environment or the root `.env`. The scripts run the dbmate binary from the `dbmate` npm package with `DBMATE_MIGRATIONS_DIR` set to `db/migrations` and `DBMATE_NO_DUMP_SCHEMA`, since dbmate's own dump needs a `pg_dump` on the host that matches the server.

The app database (`usg`) is created by `pnpm migrate`, from `template1`. The PostGIS image's init script loads PostGIS, topology and the tiger geocoder into `POSTGRES_DB`, so the compose file keeps that as `postgres`: the app database then holds only what the migrations create, the dump stays clean, and the initial migration's down section can drop PostGIS.

## Seed script

`pnpm db seed` loads `seed/core-venues.ts` into HEAD on `DATABASE_URL`'s database: the MVP's five core venues on the Esplanade corridor with their real names and kinds (Esplanade MRT and City Hall MRT as MRT stations, Raffles City and Marina Square as malls, and South Beach, a mixed-use development, as `other`). Their `permission` is null: scanning needs no venue permission (decided 2026-10-17). Funan and CityLink Mall, seeded before that, are in the dataset's `remove` list, so a re-run takes them out of HEAD; they return with the same ids in the first expansion. Their levels, footprints and operators are TODO until the owner's site walk: signage is never guessed, because a level, once created, changes only through change sets. Seeded rows reach the public files only inside a version that publishes a change set ([CLAUDE.md](../CLAUDE.md)).

The mechanism (`src/seed.ts`, exported as `@usg/db/seed`; [0004](../docs/decisions/0004-storage-and-versioning.md)):

- It inserts the venues and levels the dataset lists and HEAD lacks. Once a row exists, it writes only `venues.permission`, which no diff carries, so it bumps no `rev`; every other column changes only through change sets, so a re-run never undoes an approved change such as a measured `elevation_m` or a renamed level. Where HEAD differs from the dataset, it says so and leaves HEAD alone.
- It removes a venue or level only when the dataset names it under `remove`, and only when nothing references it (no space, node, edge, POI, anchor or restricted zone on a level; no level or zone on a venue). Otherwise it refuses, and writes nothing.
- It runs in one transaction holding `map_head FOR UPDATE`, so it never interleaves with a publish. Running it twice changes nothing.
- It refuses a database that holds the demo map, unless the dataset is the demo's own (`seed(client, dataset, { demo: true })`).

The demo map (`pnpm demo`, in `services/api`) loads its own venues and levels through the same mechanism, from a dataset of its own. The two never share a database. `src/demo.ts` (`@usg/db/demo`) has the demo's markers: `DEMO_OWNER`, the demo's owner contributor, whose row marks a database that holds the demo, `DEMO_CHANGE_SET`, and `holdsDemo(client)`. `pnpm db seed` refuses such a database ("Run `pnpm demo --reset` first"), and so does the publish (`services/api`), so real data never goes in beside demo data, where the demo's reset would then refuse to wipe it. If the stack isn't running, `pnpm db seed` says which host and port didn't answer and how to start it.

`src/local.ts` (`@usg/db/local`) has `recreateLocalDatabase(url)`: drop the database (closing its connections) and migrate it again, for `pnpm demo --reset`. It refuses a server that isn't on this machine and the server's maintenance databases. "On this machine" is `isLocalHost(url)` (also behind `pnpm db rollback` and the demo's guard), read as the drivers read the URL: its host is loopback (`localhost`, 127.0.0.0/8, `::1`), node-postgres's own parse of it (`pg-connection-string`) agrees, and it has no `host`, `hostaddr` or `service` query parameter, any of which node-postgres or dbmate's lib/pq would connect to instead.

## The schema snapshot

`pnpm db dump` applies every migration to a scratch database, runs `pg_dump --schema-only --no-owner --no-privileges` inside the PostGIS container (`docker compose exec postgis`, or `docker exec $PG_CONTAINER` in CI), and drops the scratch database. It then removes what changes between runs or servers (the `\restrict` lines with their random key, the version comments, CRLF and runs of blank lines), adds a generated-file header and appends the applied versions in dbmate's format. The output is the same on Windows and Linux. CI's `Database (postgis)` job regenerates it and fails on a diff.

The snapshot is schema only: the `map_head` row that the initial migration inserts is not in it, so build databases with `pnpm migrate`, never from `schema.sql`.

## Rule tests

Each rule in the schema has a test with a passing case and a refused case. A refused case checks why it was refused, not just that it failed: the SQLSTATE plus the constraint name (CHECK, UNIQUE, FOREIGN KEY) or the trigger's message. The fixtures are synthetic, at real City Hall cluster coordinates; the restricted zones are made up, never real outlines.

- The global setup migrates a template database with dbmate. Each test file copies it into its own database, so files run in parallel, and drops it afterwards; the developer's `usg` database is never opened. All of these are named `usg_scratch_<epoch ms>_<label>_<hex>`, and a run drops any left over from a crashed run more than an hour old.
- Inside a file, tests run in a transaction that is rolled back (`db.rolledBack`). Deferred rules fire at COMMIT ("every version except a rollback publishes a change set"), so their tests commit for real (`db.committed`, `db.expectCommitRefused`) in the file's own database.
- A change to a rule goes in a new migration with its tests in the same change.
- Other packages' database tests reuse all this rather than a harness of their own: `@usg/db/test/global-setup` as their Vitest `globalSetup`, `useDatabase` from `@usg/db/test/harness` (whose `url` lets them open their own pools on the file's database), and the fixtures in `@usg/db/test/fixtures`. `services/api` does.
